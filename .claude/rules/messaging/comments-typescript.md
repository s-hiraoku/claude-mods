# コメント規約 (TypeScript / JavaScript)

## 原則：コメントは書かないのが既定

- **既定はコメント無し。コードを読めば分かる状態が理想であり、それを最優先で目指す。**
- まず命名・関数分割・型でコードに語らせる。コメントを足す前に、コードで表現できないか必ず先に検討する。
- コメントは上記をやり尽くしても「なぜ（why）」がコードから読み取れない場合に限る、例外的な手段。
- このルールはコメントを増やすためのものではない。不要なコメントを書かないための判断基準である。
- **JSDoc も例外ではなく、この「既定はコメント無し」の対象。** public な API であっても、型・命名で契約が伝わるなら書かない。型から読めない契約がある場合に限り書く（下記「書いてよいコメント」の「利用者向け契約の JSDoc」を参照）。
- 書く場合、コード内コメントは標準語の日本語で記述する。

## 判断基準（この2つを両方満たすときだけ書く）

1. **半年後テスト**: このコメントは半年後に読んで意味が分かり、かつ *コードを読めば分かること以上* を語っているか？
2. **自己完結テスト（アンカー）**: コメントが参照を含む場合、その参照先は「*将来も安定して解決でき、時間が経っても真であり続けるアンカー*」か？（参照を含まないコメントは判断基準1のみで判定する）
   - ⭕ アンカー: Issue/PR 番号・仕様/RFC/URL・**コード内の安定識別子**（関数名/型名）・恒久的な外部仕様や挙動
   - ❌ 非アンカー: 過去の変更・会話・レビュー・自分の編集行為・実装過程・位置（上記/以下/行番号）

どちらか No なら、書かない。または下の「書き換えパターン」で直す。

## 書いてはいけないコメント

1. **コードから自明**（命名・型・処理から読み取れる）

   ```ts
   // ❌ 変数名・型で自明
   // ユーザー名をセットする
   const userName = user.name;
   ```

2. **what の逐語訳**（直後のコードの言い換え）

   ```ts
   // ❌ 直後のコードそのもの
   // ヘッダーを設定する
   req.headers = buildHeaders();
   ```

3. **装飾セクション見出し・罫線バナー**（区切り・ラベルだけのコメント。本番/テストを問わず）

   ```ts
   // ❌ 構造は命名・関数分割・ファイル分割で表現する
   // ===========================
   // State / Data / Actions
   // 型定義
   ```

   区切りたくなったら、それは関数やファイルを分ける合図。

4. **経緯・会話・実装過程・思考の吐露・scaffold の残骸**（*今も真である理由* 以外の文脈）

   ```ts
   // ❌ どれも会話/時系列に依存し、単体で読めない・やがて腐る
   // レビューで指摘されたので修正
   // 最初 xx で試したが効果がなかったので ∆∆ にした
   // ここがわからないが、そうとも言える
   // 移植元と同じフォーマット
   // パスは実際の場所に合わせてください
   ```

   経緯は PR・Issue・コミットメッセージへ。コードには「今も真である理由」だけを残す。

5. **暫定マーカー（追跡番号なし）**

   ```ts
   // ❌ 「いつ消えるか」を誰も追えない
   // TODO: とりあえず仮で設定
   // 一旦こうしておく / 今は未使用だが将来使うので残す
   ```

   → 追跡 Issue を立てて `TODO(#1234):` にする。立てられないなら消す。

6. **旧コードのコメントアウト残し**

   ```ts
   // ❌ 履歴は git にある。「将来使うかも」も含めて消す
   // const handleExport = useCallback(() => { ... })
   ```

7. **位置依存の参照**（並び替え・移動で腐る）

   ```ts
   // ❌ 「上記/以下/後述/↑」「他ファイルの行番号」「自ファイルのパス」
   // ↑の関数でカーソルを末尾へ移動
   // 原因と思われる箇所 => Foo.tsx : line 87~95
   ```

   → 参照するなら **安定した識別子名** で（例:「`useFooEditor` の初回 onChange に依存する」）。

8. **テストの逐語コメント**（`expect` の言い換え・`describe`/`it` と重複する見出し）

   ```ts
   // ❌ it('...') が既に意図を語っている
   // showLabel プロパティのテスト
   // URL.createObjectURL が呼ばれたか
   ```

   テストコメントは「なぜこの入力/前提か」の非自明な点だけに限る。

9. **型・名前を言い換えただけの JSDoc**

   ```ts
   // ❌ 型で分かることの再掲。@returns をフィールドごとに列挙して水増ししない
   /** @param schema - Zod バリデーションスキーマ */
   ```

## 書いてよいコメント（閉じた許可リスト）

以下に当てはまる場合 *だけ* 書いてよい。いずれも上の判断基準を満たすこと。

1. **コードから読めない理由・制約（why）**

   ```ts
   // ✅ 外部仕様/ブラウザ/フレームワークの制約
   // new Date(str) の解釈は Safari でランタイム依存のため date-fns の parse を使う
   // /publish は status=stopping を受け付けないため、停止時は /update を使う
   ```

2. **非自明な意思決定の根拠**（時間非依存に書く）

   ```ts
   // ✅ なぜこの分岐/設計かを、恒久的な事実として
   // 「設定を保存」は常に保存できる必要があるため、確認画面の validate 結果は含めない
   ```

3. **追跡番号付きの作業マーカー**（前方向き・番号必須）

   ```ts
   // ✅ #番号は別の追跡 Issue/PR（自己参照ではない）
   // TODO(#4083): 専用権限の導入まで lineSend で代用する
   ```

4. **安定した外部権威への参照**（仕様/RFC/URL/既知バグ）

   ```ts
   // ✅ 恒久的に解決できるアンカー
   // ref: https://swr.vercel.app/docs/revalidation#disable-automatic-revalidations
   ```

5. **コード内の安定識別子への相互参照**（位置ではなく名前で）

   ```ts
   // ✅ 「上記」ではなく識別子で
   // 初期化エラーは EditAtomProvider 側でハンドリングするためここでは無視する
   ```

6. **削除条件付きの互換シム / 意図的な握り潰し**

   ```ts
   // ✅ 「いつ消せるか」が書いてある / 空 catch の意図
   // API v2 廃止後に削除可。現行は v1 併存のため両対応する
   ```

7. **図・真理値表・変換例（`@example`）**（コードから復元しにくい仕様の可視化）

   ```ts
   // ✅ 端数配布・座標・状態組合せを図/表/例で示す
   // 例: size=1040, parts=3 -> [347, 347, 346]
   ```

   ただし寸法などの **定数値の再掲** は避ける（定数と二重管理になり腐る）。

8. **利用者向け契約の JSDoc**
   - 型から読めない **制約・単位・非自明な既定値・副作用・例外** のみを書く。`@returns` はオブジェクト1件につき1行。

9. **機械可読ディレクティブ（lint 抑制など）**
   - `eslint-disable` / `biome-ignore` などは削除対象外。ただし **必ず理由を1行添える**（特に `exhaustive-deps` / `no-danger` / `no-array-index-key` / `no-explicit-any`）。
   - リポジトリが要求するライセンス/著作権ヘッダ（SPDX 等）も削除対象外（理由は不要）。

   ```ts
   // ✅ なぜ無効化してよいかを書く
   // eslint-disable-next-line react/no-danger -- convertXxx でサニタイズ済み
   ```

10. **`@deprecated`**
    - 必ず **代替 API と削除条件** をセットで書く（`@deprecated getFoo を使用。bar 移行後に削除`）。`@deprecated` 単体（代替・削除条件なし）は不可。

## 困ったときの書き換えパターン

- **履歴 → 不変条件**: 「以前 xx で不具合が出たので直した」→「空配列だと後続の `reduce` が TypeError になるため早期 return」。情報（危険性）は残し、履歴（以前/直した）は捨てる。
- **暫定 → 追跡番号**: 「一旦こうしておく」→ Issue を立てて `TODO(#1234): …`。立てられないなら消す。
- **混在コメントは分解**: 1コメントに *恒久 why* と *腐る参照/思考の吐露* が同居していたら、悪い半分だけ削り why を残す。**1コメント = 1主張**。
