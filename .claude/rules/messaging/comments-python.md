# コメント規約 (Python)

## 原則：コメントは書かないのが既定

- **既定はコメント無し。コードを読めば分かる状態が理想であり、それを最優先で目指す。**
- まず命名・関数分割・型ヒントでコードに語らせる。コメントを足す前に、コードで表現できないか必ず先に検討する。
- コメントは上記をやり尽くしても「なぜ（why）」がコードから読み取れない場合に限る、例外的な手段。
- このルールはコメントを増やすためのものではない。不要なコメントを書かないための判断基準である。
- 書く場合、コード内コメントは標準語の日本語で記述する。

## docstring は「コメント」ではなく API ドキュメント（別枠）

- public な module / クラス / 関数・メソッドには docstring（PEP 257）を付けてよい。実装内コメントではなく **利用者向けの契約** なので、冒頭の「既定はコメント無し」原則の対象外（＝書いてよい）。ただし内容は下記の品質基準に従い、逐語訳・型ヒントの再掲はしない。
- docstring には **利用者が知るべき契約**（責務・引数・戻り値・送出する例外・副作用）を書く。実装の逐語訳や、型ヒントから自明な引数説明は書かない。
- private / 内部ヘルパ（`_foo`）で、名前と型ヒントから契約が自明なものには docstring を付けない。

## 判断基準（この2つを両方満たすときだけ書く）

1. **半年後テスト**: このコメントは半年後に読んで意味が分かり、かつ *コードを読めば分かること以上* を語っているか？
2. **自己完結テスト（アンカー）**: コメントが参照を含む場合、その参照先は「*将来も安定して解決でき、時間が経っても真であり続けるアンカー*」か？（参照を含まないコメントは判断基準1のみで判定する）
   - ⭕ アンカー: Issue/PR 番号・仕様/RFC/URL・**コード内の安定識別子**（関数名/クラス名）・恒久的な外部仕様や挙動
   - ❌ 非アンカー: 過去の変更・会話・レビュー・自分の編集行為・実装過程・位置（上記/以下/行番号）

どちらか No なら、書かない。または下の「書き換えパターン」で直す。

## 書いてはいけないコメント

1. **コードから自明**（命名・型ヒント・処理から読み取れる）

   ```python
   # ❌ 変数名・型で自明
   # ユーザー名をセットする
   user_name = user.name
   ```

2. **what の逐語訳**（直後のコードの言い換え）

   ```python
   # ❌ 直後のコードそのもの
   # ヘッダーを設定する
   headers = build_headers()
   ```

3. **装飾セクション見出し・罫線バナー**（区切り・ラベルだけのコメント。本番/テストを問わず）

   ```python
   # ❌ 構造は命名・関数分割・モジュール分割で表現する
   # ===========================
   # Constants / Types / Utils
   ```

   区切りたくなったら、それは関数やモジュールを分ける合図。

4. **経緯・会話・実装過程・思考の吐露・scaffold の残骸**（*今も真である理由* 以外の文脈）

   ```python
   # ❌ どれも会話/時系列に依存し、単体で読めない・やがて腐る
   # レビューで指摘されたので修正
   # 最初 xx で試したが効果がなかったので ∆∆ にした
   # 移植元と同じフォーマット
   # パスは実際の場所に合わせてください
   ```

   経緯は PR・Issue・コミットメッセージへ。コードには「今も真である理由」だけを残す。

5. **暫定マーカー（追跡番号なし）**

   ```python
   # ❌ 「いつ消えるか」を誰も追えない
   # TODO: とりあえず仮で設定
   # 一旦こうしておく / 今は未使用だが将来使うので残す
   ```

   → 追跡 Issue を立てて `TODO(#1234):` にする。立てられないなら消す。

6. **旧コードのコメントアウト残し**

   ```python
   # ❌ 履歴は git にある。「将来使うかも」も含めて消す
   # result = old_impl(payload)
   ```

7. **位置依存の参照**（並び替え・移動で腐る）

   ```python
   # ❌ 「上記/以下/後述/↑」「他ファイルの行番号」「自ファイルのパス」
   # 原因と思われる箇所 => foo.py : 87~95 行
   ```

   → 参照するなら **安定した識別子名** で（例:「`FooParser` の初回呼び出しに依存する」）。

8. **テストの逐語コメント**（`assert` の言い換え・`class Test...` / テスト関数名と重複する見出し）

   ```python
   # ❌ テスト関数名が既に意図を語っている
   # show_label 引数のテスト
   # download が呼ばれたか
   ```

   テストコメントは「なぜこの入力/前提か」の非自明な点だけに限る。

9. **型・名前を言い換えただけの docstring / 引数説明**

   ```python
   # ❌ 型ヒントで分かることの再掲
   def get_inflow_settings() -> list[InflowSetting]:
       """流入設定のリストを返す"""
   ```

## 書いてよいコメント（閉じた許可リスト）

以下に当てはまる場合 *だけ* 書いてよい。いずれも上の判断基準を満たすこと。

1. **コードから読めない理由・制約（why）**

   ```python
   # ✅ 外部仕様/ライブラリ/ランタイムの制約
   # API が未計測を None で返す仕様のため、未計測は 0 とみなす
   count = response.count if response.count is not None else 0
   ```

2. **非自明な意思決定の根拠**（時間非依存に書く）

   ```python
   # ✅ なぜこの設計かを、恒久的な事実として
   # 仕様上、削除済みフローも履歴表示で参照されるため物理削除しない
   ```

3. **追跡番号付きの作業マーカー**（前方向き・番号必須）

   ```python
   # ✅ #番号は別の追跡 Issue/PR（自己参照ではない）
   # TODO(#4083): 専用権限の導入まで既存権限で代用する
   ```

4. **安定した外部権威への参照**（仕様/RFC/URL/既知バグ）

   ```python
   # ✅ 恒久的に解決できるアンカー
   # ref: https://docs.python.org/3/library/datetime.html#datetime.datetime.fromisoformat
   ```

5. **コード内の安定識別子への相互参照**（位置ではなく名前で）

   ```python
   # ✅ 「上記」ではなく識別子で
   # 初期化エラーは AppContext 側で送出するためここでは握らない
   ```

6. **削除条件付きの互換シム / 意図的な握り潰し**

   ```python
   # ✅ 「いつ消せるか」が書いてある / 例外を意図的に無視する理由
   # v2 API 廃止後に削除可。現行は v1 併存のため両対応する
   ```

7. **図・真理値表・変換例**（コードから復元しにくい仕様の可視化）

   ```python
   # ✅ 状態組合せ・変換規則を表/例で示す
   # 例: size=1040, parts=3 -> [347, 347, 346]
   ```

   ただし定数値の再掲は避ける（定数と二重管理になり腐る）。

8. **利用者向け契約の docstring**（上の「別枠」節を参照）
   - 型ヒントから読めない **制約・単位・非自明な既定値・副作用・送出例外** のみを書く。

9. **機械可読ディレクティブ（lint / 型チェック抑制など）**
   - `# noqa` / `# type: ignore` / `# pylint: disable` などは削除対象外。ただし **必ず理由を1行添える**。
   - リポジトリが要求するライセンス/著作権ヘッダ（SPDX 等）も削除対象外（理由は不要）。

   ```python
   # ✅ なぜ無効化してよいかを書く
   value = data["x"]  # type: ignore[index]  # 上流で存在保証済み
   ```

10. **非推奨マーキング**
    - `warnings.warn(..., DeprecationWarning)` や `@deprecated`（typing 版）を使い、docstring に **代替 API と削除条件** をセットで書く。単に `# deprecated` とだけ書かない。

## 困ったときの書き換えパターン

- **履歴 → 不変条件**: 「以前 xx で不具合が出たので直した」→「空リストだと後続の `reduce` が例外になるため早期 return」。情報（危険性）は残し、履歴（以前/直した）は捨てる。
- **暫定 → 追跡番号**: 「一旦こうしておく」→ Issue を立てて `TODO(#1234): …`。立てられないなら消す。
- **混在コメントは分解**: 1コメントに *恒久 why* と *腐る参照/思考の吐露* が同居していたら、悪い半分だけ削り why を残す。**1コメント = 1主張**。
